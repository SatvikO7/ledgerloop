# LedgerLoop

**A three-way reconciliation agent with an honest exception list.**

Reconciles the internal ledger, PSP settlements, and bank statements across heterogeneous
formats — solving the many-payments-to-one-payout aggregation problem deterministically,
calling an LLM only on the residual, and reporting every exception with a typed root
cause, an evidence chain, and a rupee figure.

| On `test`, 5 seeds, standard difficulty | |
|---|---|
| **Auto-match precision** | **1.0000 ± 0.0000** — 0 false positives across all 5 runs, ₹0 of wrong money |
| **Link recall** | 0.8049 ± 0.0792 |
| **Match rate** | 0.7711 ± 0.0861 *(target ≥ 0.85 — see [Limitations](#limitations-stated-rather-than-buried))* |
| **Exception recall** | 0.9818 ± 0.0250 |
| **LLM calls** | **0** — every number above is deterministic and reproducible with no API key |

Every proportion in [EVALUATION.md](EVALUATION.md) carries its sample size and a 95%
Wilson interval, and every number in it is regenerated by one command.

```bash
uv venv --python 3.11 && uv pip install -e ".[demo]"
python -m ledgerloop.cli demo          # generate, calibrate, reconcile, open the UI
```

Full instructions in **[DEMO.md](DEMO.md)**. No API key, no database, no Docker, no Make.

## The problem

Three systems describe the same money and none of them agrees:

- the **internal ledger** knows what was ordered,
- the **PSP settlement report** knows what was batched and what fees were taken,
- the **bank statement** knows what actually arrived.

The hard part is not string matching. It is that **many payments become one payout**: a
settlement nets dozens of payments minus a fee, and the bank sees one credit with a
narration like `NEFT-UTR2026030946866-ZRDHA BRKNG L-MERCHANT PAYOUT`. Recovering which
payments are inside that credit is a subset-sum problem, and it has to be solved without
guessing — a wrong auto-match costs a finance team far more than a human reviewing an
extra item.

## What it does

| | |
|---|---|
| **Three-way, not two-way** | Ledger ↔ PSP ↔ bank, with the fee-and-netting layer in the middle |
| **Deterministic aggregation** | a subset-sum solver that **counts** solutions and refuses when two fit |
| **A fitted confidence model** | probabilities fitted on a held-out split, with a threshold selected for precision — **and a report that says plainly that this corpus does not exercise it** |
| **Typed exceptions** | class, severity, ₹ impact, evidence chain, root cause, suggested action |
| **An audit trail you can replay** | every decision, its tier, its score and its evidence, append-only |
| **LLM last and bounded** | it proposes; it never decides, never does arithmetic, never produces a metric |

## Architecture

```
                    three heterogeneous sources
        ledger_orders.csv · psp_settlements.json · bank_statement.csv
                                  │
                                  ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │                  LangGraph state machine (agent/)                 │
   │                                                                   │
   │  ingest → normalize → build_entity_graph → tier_ladder ⟲          │
   │         → llm_adjudicate → calibrate_and_decide                   │
   │         → classify_exceptions → explain → measure → report        │
   └───────┬──────────────────────────────────────────────────────────┘
           │ every node calls a tested function; the graph computes nothing
           ▼
   ┌───────────────────────────┐   ┌──────────────────────────────────┐
   │  matching/  the tier ladder│   │  exceptions/  the typed queue    │
   │  T0 exact key              │   │  class · severity · ₹ · evidence │
   │  T1 tolerance              │   │  bounded auto-resolution         │
   │  T2 aggregation (subset-sum)   └──────────────────────────────────┘
   │  T3 lexical (derived master)│
   │  T4 graph inference         │   ┌──────────────────────────────────┐
   │  T5 LLM  ← proposes only    │   │  eval/  metrics, baselines,      │
   └───────────────────────────┘   │  ablation, calibration, report   │
                                    └──────────────────────────────────┘
           │
           ▼
   reports/runs/<run_id>/          EVALUATION.md
   run.json · audit.jsonl          every number, regenerated by one command
   exceptions.json · decisions.json
           │
           ▼
   ui/  four screens: Run · Results · Exceptions · Audit replay
        reads the four files; computes nothing
```

`tier_ladder` is a **real cycle**. T2/T3/T4 repeat while a pass keeps adding candidates,
because resolving one bank credit constrains the remaining ones. That loop, the
conditional branch, and per-node checkpointing are the only things LangGraph is claimed
for — the reconciliation logic lives in `matching/` and is called, not reimplemented. A
test asserts the graph and a plain function chain produce identical predictions,
decisions, tier tables and metrics, for every tier configuration.

### Deterministic first, LLM last

The ladder runs in order and each tier sees only what the previous ones left:

| Tier | How it decides | Deterministic? |
|---|---|---|
| **T0** exact key | UTR / order reference, exact amount | yes |
| **T1** tolerance | ±0.5% or ₹1, ±3 days, **mutual** uniqueness both ways | yes |
| **T2** aggregation | meet-in-the-middle subset-sum, anchored on the settlement; **counts** solutions and refuses when two fit | yes |
| **T3** lexical | merchant master **derived from the statement's own references**, RapidFuzz, score and margin gates | yes |
| **T4** graph | path closure, sibling completion, exclusivity over an in-memory graph | yes |
| **T5** LLM | proposes a link and a hypothesis for the residual | **no — and it never decides** |

Everything T5 returns passes three gates it cannot see around: a strict schema, a
grounding check against the evidence pack it was given, and `verify_arithmetic`, which
re-derives the money from the source documents and **has no parameter for where a
proposal came from** — there is a test asserting that. A proposal whose money does not
close is *demoted, not dropped*: it becomes a candidate routed to a human, because "the
model suggested this and the arithmetic disagrees" is information a controller wants.

The model's self-reported confidence is a **feature**, never a probability. A proposal
asserting 0.99 would otherwise auto-match itself, which is the one thing the design
forbids.

T5 reaches a provider through a **failover ladder** — Groq → Gemini → OpenRouter →
Ollama — behind the same one-method protocol, so the cache, the budget, the validation, the
gates and the cost ledger sit exactly where they were. A rate limit waits once and moves
down a rung; an outage moves down immediately; an exhausted ladder raises, and every call
site treats that exactly like `--no-llm`. How far down a run had to go is recorded as
`fallback_depth` so a rate-limited run is visible in the report rather than silent. Keys
come from the environment (`GROQ_API_KEY`, `GEMINI_API_KEY`, `OPENROUTER_API_KEY`, or the
shared `LEDGERLOOP_LLM_API_KEY`); see [`.env.example`](.env.example). **A machine with no
key builds no ladder and runs deterministically.**

**`--no-llm` runs the entire system with no model and no network**, and produces a
byte-identical report. Every number published here was produced that way.

### How a decision is made

Each candidate carries a feature vector and an evidence chain. A logistic blender scores
it, an isotonic calibrator turns the score into a probability, and a fitted threshold
routes it:

```
p ≥ τ_high  → AUTO_MATCHED     committed, arithmetic verified
τ_low < p < τ_high → NEEDS_REVIEW   a person looks at it
p ≤ τ_low   → EXCEPTION        escalated with a typed reason
```

`τ_high` is **selected on the calibration split** as the lowest threshold achieving the
precision target — never hand-picked, and never fitted on `test`. `CalibrationProvenance`
refuses to construct a bundle whose halves overlap or whose either half is the test split,
so the discipline is a type error rather than a convention.

**On this corpus that middle band is empty, and the report says so in one paragraph
rather than leaving it to be assembled.** The residual tiers refuse rather than guess, so
the fit population is single-class: the logistic's coefficients come out numerically zero,
the isotonic map collapses to one block, `τ_high` fits at exactly 1.0, and probabilities
are bimodal at 0.5 and 1.0 with nothing in between. `NEEDS_REVIEW` therefore fires **zero**
times and the three-way policy behaves two-way. **Remove the calibration layer and every
published number is identical.** What it buys is the shape: the day a tier starts proposing
things that are sometimes wrong, the fitted model and the held-out split are already there.
`EVALUATION.md` derives that paragraph from the fitted bundle at render time, so it cannot
survive the fit ceasing to be degenerate.

## Evaluation methodology

Three splits, kept strictly apart: `train` fits the blender, `calibration` fits the
isotonic map and selects `τ_high`, **`test` is only ever scored**. Every published number
is regenerated by one command (`make eval`), nothing in `EVALUATION.md` is hand-typed, and
two runs of it differ only in a labelled block of measured timings.

The unit of evaluation is the `PAYMENT_CREDITED_AS` link — a `(payment, bank_txn)` pair.
Structural edges the sources already assert are excluded; counting them would inflate
every score.

- **Every headline proportion travels with its sample size and a 95% Wilson interval** —
  precision, link recall, match rate, exception recall and the unmatchable floor. Not the
  normal approximation, which collapses to `[1.0, 1.0]` at these sample sizes and claims
  certainty the data cannot support. The report's verdict column reads the *interval*,
  one-sided: *met* when the lower bound clears the target, *missed* when the upper bound is
  below it, and *undecided* when it straddles — which is why 30 of 30 exceptions is reported
  as not demonstrating ≥ 0.95 from thirty records rather than as a pass.
- **A before/after study for the one substantive change**, both arms over the same fifteen
  corpora with the same bundle, differing in exactly one configuration field, with each
  arm's `tuning_hash` printed so "nothing else changed" is a check.
- **Four baselines on the same ground truth** — exact join, exact + fuzzy, LLM-only, and
  the full system.
- **A six-row ablation**, re-run rather than subtracted: the tiers share a pool, so
  switching one off leaves its settlements for the next, and reading the table off one
  run's counters would describe an arithmetic identity rather than a system.
- **Five seeds, three difficulties, mean ± sample std.** A single run's number is noise.

## Generating data

```bash
ledgerloop generate --split test --difficulty standard --seed 42
```

Ground truth is generated **first**, and the data is derived from it — never inferred
afterwards. Generation is a pure function of `(seed, split, difficulty, order_count)`, so the
same command twice produces byte-identical files and anyone can reproduce every number.

| Split | Orders | Purpose |
|---|---|---|
| `dev` | 60 | fast iteration; meets the challenge's 50+ bar |
| `train` | 400 | fits the score blender |
| `calibration` | 200 | fits isotonic calibration and selects thresholds — never evaluated on |
| `test` | 300 | every published number comes from here |
| `scale` | 5,000 | supported by the generator (~1.5 s to generate); **not benchmarked** |

Eleven anomaly classes are injected at controlled prevalence, with a `--difficulty
{easy,standard,hard}` dial that changes *how much* goes wrong without changing *what* goes
wrong. Money conservation is enforced as a property test: the bank credits reconcile to the
declared settlement nets exactly, modulo the deltas each anomaly explicitly declares.

A committed 60-order fixture set lives in `data/fixtures/dev-standard-42/`.

The data model and the definitions the evaluation depends on are documented in the modules
themselves — `models/truth.py` for the link-level ground truth, `eval/metrics.py` for the
metric definitions, and `money.py` for the integer-minor-unit invariant. The `§` references
in those docstrings point at an internal design document that is not published.

## The demo

```bash
uv venv --python 3.11
uv pip install -e ".[demo]"          # adds LangGraph + Streamlit
python -m ledgerloop.cli demo        # or: make demo
```

It generates the corpora, fits the calibration bundle on `train` and `calibration`
(never on `test`), reconciles the **300-order `test` corpus** — 742 records, 294 evaluation
links — through the LangGraph pipeline, and opens the four-screen interface on the result.
It skips corpora that already exist, so it is safe to re-run. **[DEMO.md](DEMO.md)** has the
same steps one at a time, the prerequisites, and the troubleshooting table.

**The demo opens on `test` deliberately.** That is the corpus every number in this file and
in `EVALUATION.md` is measured on, so the figures on screen are the figures the documents
contain. `--split dev` runs the 60-order corpus instead — it still clears the challenge's
50+ record bar and is faster, but its exception recall rests on five records and means very
little.

| Screen | What it shows |
|---|---|
| **Run** | generate or pick a dataset, apply the fitted bundle, reconcile |
| **Results** | precision with its Wilson interval, match rate, recall, exception recall, ₹ reconciled against ₹ outstanding, the tier waterfall, per-class recall |
| **Exceptions** | the queue sorted by ₹ impact, each row with a class, a severity, a price, an evidence chain and a suggested action |
| **Audit replay** | step any record through the tiers: which one proposed it, what it scored, what the policy returned, and why |

`AUTO_MATCHED`, `NEEDS_REVIEW`, `EXCEPTION` and `REJECTED` are always four separate
figures. Unresolved exceptions are shown as unresolved, and the `UNMATCHABLE` floor is
labelled as a real ceiling rather than folded into a failure.

The **Run** tab reconciles any other corpus on disk, including the 300-record `test` split.
Each run writes `reports/runs/<run_id>/` — `run.json`, `audit.jsonl` (append-only, the
replay's source), `exceptions.json`, `decisions.json` — and the UI reads those four files
and computes nothing.

Without the extras, everything that produces a number still works:

```bash
uv pip install -e ".[dev]"
make eval                            # regenerates EVALUATION.md — no LangGraph, no Streamlit
```

## Results

Every number below is regenerated by one command (`make eval`) and written into
`EVALUATION.md`. Nothing in that document is hand-typed and nothing in it comes from a
language model — the metrics are produced by deterministic code, scored against
link-level ground truth read back off disk.

**The four-system comparison**, `test` split, seed 42 (B2 on the 60-order `dev` split):

| # | System | Precision | Recall | Match rate | False positives | FP cost |
|---|---|---|---|---|---|---|
| B0 | Exact join on UTR | 0.5909 | 0.6633 | 0.6580 | 135 | ₹34,98,306 |
| B1 | Exact + fuzzy + nearest amount | 0.6540 | 0.8810 | 0.8667 | 137 | ₹35,37,867 |
| B2 | LLM-only, output asserted unverified § | 0.7000 | 0.7119 | 0.9706 | 18 | ₹4,32,588 |
| **B3** | **LedgerLoop** | **1.0000** | **0.8435** | 0.7971 | **0** | **₹0** |

The baselines reach further on match rate; every one of them is wrong in rupees. The
deterministic ladder is never wrong, and the false-positive column is what that trade costs
a finance team. § B2 is on a **different, smaller corpus** (`dev`, 59 links vs 294) and its
prompts were answered by a documented offline stand-in, not a language model — its accuracy
figures say nothing about any model. `EVALUATION.md` banners both facts.

**Across five seeds** (`test`, standard difficulty, mean ± sample standard deviation):

```
precision  1.0000 ± 0.0000      recall  0.8049 ± 0.0792
match rate 0.7711 ± 0.0861      exception recall  0.9818 ± 0.0250
0 false positives across all five runs
```

**Each tier, priced** — six ladders × five seeds, thirty runs, zero false positives in
all of them:

| Ladder | Recall | Marginal |
|---|---|---|
| T0 | 0.3489 ± 0.0206 | +0.3489 |
| T0–T1 | 0.5123 ± 0.1019 | **+0.1634** |
| T0–T2 | 0.6625 ± 0.0565 | +0.1502 |
| T0–T3 | 0.8049 ± 0.0792 | +0.1424 |
| T0–T4 | 0.8049 ± 0.0792 | +0.0000 |

T4 fires zero times on this corpus. That is reported rather than engineered around.

**Under load** — the same configuration across the difficulty dial:

| | easy | standard | hard |
|---|---|---|---|
| Recall | 0.8776 ± 0.0363 | 0.8049 ± 0.0792 | 0.7414 ± 0.1048 |
| Match rate | 0.8571 ± 0.0389 | 0.7711 ± 0.0861 | 0.7063 ± 0.1020 |
| Exception recall | 0.9784 ± 0.0296 | 0.9818 ± 0.0250 | 0.9920 ± 0.0179 |
| Precision | 1.0000 | 1.0000 | 1.0000 |

Recall falls, exception recall rises, precision does not move: the system asserts less and
describes more as more of the corpus breaks. The `easy` column clears the ≥ 0.85 match-rate
target; `standard` and `hard` do not.

### What Phase 2 changed, measured

Recall was not being lost across payments — it was lost at the *settlement* end. On seed 42
seventeen of thirty-five bank credits were fully resolved and eighteen were not resolved at
all, with **no partially-resolved credit anywhere**. Of the 164 missing links, **118 (72%)
belonged to ten settlements whose payout the bank had posted twice**: the ladder saw two
indistinguishable credits, correctly refused to choose between them, and took the whole
batch with it.

The fix is a **duplicate-posting pass over the statement, before the ladder runs** — the
thing a controller does first. Credits that are exact re-postings of one another (same
amount to the paise, same normalised narration, distinct value dates inside a window) are
one payout posted more than once; the earliest is the payout and the later ones leave the
*matchable* pool. They are **not** removed from the report: each is still raised as an
`E_DUPLICATE_CREDIT` exception with its full amount as impact, because somebody has to
reverse it.

Both arms, same fifteen corpora, same bundle, one configuration field apart:

| | easy | standard | hard |
|---|---|---|---|
| Recall, without the pass | 0.8122 ± 0.0641 | 0.5808 ± 0.1951 | 0.4446 ± 0.1156 |
| Recall, with it | **0.8776 ± 0.0363** | **0.8049 ± 0.0792** | **0.7414 ± 0.1048** |
| Δ | +0.0654 | **+0.2240** | **+0.2967** |
| Match rate, Δ | +0.0627 | +0.2078 | +0.2749 |
| Precision | 1.0000 → 1.0000 | 1.0000 → 1.0000 | 1.0000 → 1.0000 |
| False positives | 0 → **0** | 0 → **0** | 0 → **0** |

**No threshold, tolerance or gate moved.** The pass's own two knobs can only be turned
towards asserting *less*, and switching it off reproduces every pre-Phase-2 number to the
digit — 130/0/164, recall 0.4422, match rate 0.4261, every ladder prefix and every per-class
figure to six places, asserted exactly rather than approximately by
`tests/unit/test_metrics_regression.py`.

A second, **independent** Phase 2 change took exception recall from the 0.8753 ± 0.0689
the previous release reported to **0.9818 ± 0.0250**: orders refunded *after* their own
payout, whose claw-back is netted off a later batch, are now attributed to the refunded
order the ledger itself marks `REFUNDED`. Nothing in the queue reached them before — the
later batch reconciles to the paise and the earlier one was paid in full — so they were
reported only by accident, when an unrelated anomaly happened to leave their batch
contested. Removing that accident is what made the gap visible.

It is genuinely independent, and the table above is where you can see that: the
`exception recall` row of the before/after study reads **+0.0000 at every difficulty**,
because both arms carry the fix. The improvement is attributable to the claw-back rule and
not to the duplicate pass, and the study says so rather than letting one change take credit
for the other. The seed-42 movement — 28 of 30 to 30 of 30 — is pinned in
`tests/unit/test_metrics_regression.py`, whose docstring records where 0.9333 came from.

**Cost.** The deterministic ladder reconciles the whole corpus with **zero** LLM calls.
Thresholds are fitted on a `calibration` split and never on `test`; the evaluation is
seeded, and two runs of `make eval` produce byte-identical output apart from one labelled
block of measured timings.

## Limitations, stated rather than buried

The uncomfortable numbers are printed in `EVALUATION.md` beside the good ones. The ones
worth knowing before you look:

- **Match rate still misses its target.** 0.7711 ± 0.0861 at standard difficulty against a
  ≥ 0.85 goal — up from 0.5633 ± 0.1956, and clearing the target on `easy` (0.8571 ± 0.0389)
  but not on `standard` or `hard`. The system asserts less than it could, on purpose; the
  precision column is what that buys and the false-positive column is what the baselines pay
  for the difference.
- **Every missing link on seed 42 is a split payout.** 46 of them, across four settlements,
  and the per-class recall for `A09_SPLIT_PAYOUT` is pinned at **0.3429 — exactly unmoved by
  Phase 2**. Three of the four are batches paid in two tranches whose narrations *also* lost
  their references, so no tier finds the tranche pair at all; the fourth is genuinely
  ambiguous, with two different payment subsets summing to the same credit inside tolerance.
  The system refuses it and says so. That is the whole of the remaining gap and it is
  reported as unmoved rather than averaged away.
- **T4 fires zero times on this corpus.** Every earlier tier matches at settlement
  granularity, so the partial assignments its rules exist to finish never arise. Reported
  as zero rather than engineered around; loosening a rule until it fired would trade
  precision for the appearance of contribution.
- **The calibration layer is numerically inert here.** The residual tiers assert nothing
  wrong across nine corpora, so the fit population is single-class: coefficients come out
  numerically zero, the isotonic map is one block, `τ_high` fits at 1.0, `NEEDS_REVIEW`
  fires zero times, and **removing the layer would change no published number**.
  "Confidence-calibrated" describes the architecture, not a demonstrated behaviour — and
  `EVALUATION.md` derives that paragraph from the fitted bundle rather than asserting it.
- **No live LLM has been run.** There is no provider key in this environment and none was
  invented. The provider ladder is built and unit-tested against fake rungs (failover,
  rate-limit retry, `Retry-After`, ladder exhaustion, cache stability), and the *production*
  LLM path was measured end to end — 16 calls, 20,087 tokens, 2.16 calls per 100 records, 35
  narration repairs accepted, 4 link proposals returned and **0 accepted** with 2 demoted by
  `verify_arithmetic`, 74 exception explanations rewritten, ₹0 actual and ₹14.27
  equivalent-paid cost — with a documented offline stand-in that reads the prompt and
  nothing else, **and a `--no-llm` control over the same corpus whose four headline figures
  are identical**. The
  artefact records `live: false` and the report prints a banner. **No claim is made here
  about any language model's answer quality.** One command produces a live measurement on a
  machine that has a key: `ledgerloop llm-report --data ... ` without `--offline-provider`.
- **`UNMATCHABLE` records are a real ceiling**, not a model failure: 67.6 ± 2.3 records
  per `test` corpus cannot be resolved from the three sources at all. They are excluded from
  the match-rate denominator and reported on their own line, because a system that
  counted them inside its recall could inflate the number by describing items nobody
  could resolve.
- **Sample sizes are small where it matters most.** Exception recall has the smallest
  denominator in the report — thirty records on seed 42 — and 30 of 30 does **not**
  demonstrate ≥ 0.95 from thirty records: the 95% Wilson interval is [0.8865, 1.0000] and
  the target sits inside it. The report calls that *undecided* rather than a pass.
- **The `scale` split has never been benchmarked.** The generator supports 5,000 orders;
  no throughput run has been made against it.
- **No CI.** For a project with 2,000+ tests the absence of a green badge is conspicuous;
  `make check` runs the same three commands locally.
- **Synthetic data only.** Eleven anomaly classes at controlled prevalence from a seeded
  generator. Nothing here has met a real bank statement.

## MVP scope

Four scope decisions taken before implementation:

| Decision | Rationale |
|---|---|
| **Neo4j cut** — NetworkX is the real implementation, behind `graph/interface.py` | The plan required both to produce identical decisions, which makes the database pure overhead |
| **ChromaDB cut** — T3 is lexical-only, behind `vector/interface.py` | Sentence embeddings are weak on vowel-dropped abbreviations; a normaliser plus fuzzy matching is better and simpler |
| **Streamlit UI** — React is stretch only | The UI is scheduled after every metric exists; two days is not a React app |
| **A11 FX/multicurrency cut** | Multicurrency forces an FX rounding policy into the money path for 2% of records |
