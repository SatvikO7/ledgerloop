# LedgerLoop

**A three-way, confidence-calibrated reconciliation agent with an honest exception list.**

Reconciles the internal ledger, PSP settlements, and bank statements across heterogeneous
formats — solving the many-payments-to-one-payout aggregation problem deterministically,
calling an LLM only on the residual, and reporting every match with a calibrated confidence
and every exception with a typed root cause, an evidence chain, and a rupee figure.

```bash
uv venv --python 3.11 && uv pip install -e ".[demo]"
python -m ledgerloop.cli demo          # ~8s: generate, calibrate, reconcile, open the UI
```

Full instructions in **[DEMO.md](DEMO.md)**. No API key, no database, no Docker, no Make.

---

## The problem

Three systems describe the same money and none of them agrees:

- the **internal ledger** knows what was ordered,
- the **PSP settlement report** knows what was batched and what fees were taken,
- the **bank statement** knows what actually arrived.

The hard part is not string matching. It is that **many payments become one payout**: a
settlement nets dozens of payments minus a fee, and the bank sees one credit with a
narration like `NEFT-UTR2026030946866-ZRDHA BRKNG L-MERCHANT PAYOUT`. Recovering which
payments are inside that credit is a subset-sum problem, and it has to be solved without
guessing — a wrong auto-match costs a finance team far more than a human reviewing an
extra item.

## What it does

| | |
|---|---|
| **Three-way, not two-way** | Ledger ↔ PSP ↔ bank, with the fee-and-netting layer in the middle |
| **Deterministic aggregation** | a subset-sum solver that **counts** solutions and refuses when two fit |
| **Calibrated confidence** | probabilities fitted on a held-out split, with a threshold selected for precision |
| **Typed exceptions** | class, severity, ₹ impact, evidence chain, root cause, suggested action |
| **An audit trail you can replay** | every decision, its tier, its score and its evidence, append-only |
| **LLM last and bounded** | it proposes; it never decides, never does arithmetic, never produces a metric |

## Architecture

```
                    three heterogeneous sources
        ledger_orders.csv · psp_settlements.json · bank_statement.csv
                                  │
                                  ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │                  LangGraph state machine (agent/)                 │
   │                                                                   │
   │  ingest → normalize → build_entity_graph → tier_ladder ⟲          │
   │         → llm_adjudicate → calibrate_and_decide                   │
   │         → classify_exceptions → explain → measure → report        │
   └───────┬──────────────────────────────────────────────────────────┘
           │ every node calls a tested function; the graph computes nothing
           ▼
   ┌───────────────────────────┐   ┌──────────────────────────────────┐
   │  matching/  the tier ladder│   │  exceptions/  the typed queue    │
   │  T0 exact key              │   │  class · severity · ₹ · evidence │
   │  T1 tolerance              │   │  bounded auto-resolution         │
   │  T2 aggregation (subset-sum)   └──────────────────────────────────┘
   │  T3 lexical (derived master)│
   │  T4 graph inference         │   ┌──────────────────────────────────┐
   │  T5 LLM  ← proposes only    │   │  eval/  metrics, baselines,      │
   └───────────────────────────┘   │  ablation, calibration, report   │
                                    └──────────────────────────────────┘
           │
           ▼
   reports/runs/<run_id>/          EVALUATION.md
   run.json · audit.jsonl          every number, regenerated by one command
   exceptions.json · decisions.json
           │
           ▼
   ui/  four screens: Run · Results · Exceptions · Audit replay
        reads the four files; computes nothing
```

`tier_ladder` is a **real cycle**. T2/T3/T4 repeat while a pass keeps adding candidates,
because resolving one bank credit constrains the remaining ones. That loop, the
conditional branch, and per-node checkpointing are the only things LangGraph is claimed
for — the reconciliation logic lives in `matching/` and is called, not reimplemented. A
test asserts the graph and a plain function chain produce identical predictions,
decisions, tier tables and metrics, for every tier configuration.

### Deterministic first, LLM last

The ladder runs in order and each tier sees only what the previous ones left:

| Tier | How it decides | Deterministic? |
|---|---|---|
| **T0** exact key | UTR / order reference, exact amount | yes |
| **T1** tolerance | ±0.5% or ₹1, ±3 days, **mutual** uniqueness both ways | yes |
| **T2** aggregation | meet-in-the-middle subset-sum, anchored on the settlement; **counts** solutions and refuses when two fit | yes |
| **T3** lexical | merchant master **derived from the statement's own references**, RapidFuzz, score and margin gates | yes |
| **T4** graph | path closure, sibling completion, exclusivity over an in-memory graph | yes |
| **T5** LLM | proposes a link and a hypothesis for the residual | **no — and it never decides** |

Everything T5 returns passes three gates it cannot see around: a strict schema, a
grounding check against the evidence pack it was given, and `verify_arithmetic`, which
re-derives the money from the source documents and **has no parameter for where a
proposal came from** — there is a test asserting that. A proposal whose money does not
close is *demoted, not dropped*: it becomes a candidate routed to a human, because "the
model suggested this and the arithmetic disagrees" is information a controller wants.

The model's self-reported confidence is a **feature**, never a probability. A proposal
asserting 0.99 would otherwise auto-match itself, which is the one thing the design
forbids.

**`--no-llm` runs the entire system with no model and no network**, and produces a
byte-identical report. Every number published here was produced that way.

### How a decision is made

Each candidate carries a feature vector and an evidence chain. A logistic blender scores
it, an isotonic calibrator turns the score into a probability, and a fitted threshold
routes it:

```
p ≥ τ_high  → AUTO_MATCHED     committed, arithmetic verified
τ_low < p < τ_high → NEEDS_REVIEW   a person looks at it
p ≤ τ_low   → EXCEPTION        escalated with a typed reason
```

`τ_high` is **selected on the calibration split** as the lowest threshold achieving the
precision target — never hand-picked, and never fitted on `test`. `CalibrationProvenance`
refuses to construct a bundle whose halves overlap or whose either half is the test split,
so the discipline is a type error rather than a convention.

## Evaluation methodology

Three splits, kept strictly apart: `train` fits the blender, `calibration` fits the
isotonic map and selects `τ_high`, **`test` is only ever scored**. Every published number
is regenerated by one command (`make eval`), nothing in `EVALUATION.md` is hand-typed, and
two runs of it differ only in a labelled block of measured timings.

The unit of evaluation is the `PAYMENT_CREDITED_AS` link — a `(payment, bank_txn)` pair.
Structural edges the sources already assert are excluded; counting them would inflate
every score.

- **Precision travels with a Wilson interval**, not the normal approximation, which
  collapses to `[1.0, 1.0]` at these sample sizes and claims certainty the data cannot
  support.
- **Four baselines on the same ground truth** — exact join, exact + fuzzy, LLM-only, and
  the full system.
- **A six-row ablation**, re-run rather than subtracted: the tiers share a pool, so
  switching one off leaves its settlements for the next, and reading the table off one
  run's counters would describe an arithmetic identity rather than a system.
- **Five seeds, three difficulties, mean ± sample std.** A single run's number is noise.

## Generating data

```bash
ledgerloop generate --split test --difficulty standard --seed 42
```

Ground truth is generated **first**, and the data is derived from it — never inferred
afterwards. Generation is a pure function of `(seed, split, difficulty, order_count)`, so the
same command twice produces byte-identical files and anyone can reproduce every number.

| Split | Orders | Purpose |
|---|---|---|
| `dev` | 60 | fast iteration; meets the challenge's 50+ bar |
| `train` | 400 | fits the score blender |
| `calibration` | 200 | fits isotonic calibration and selects thresholds — never evaluated on |
| `test` | 300 | every published number comes from here |
| `scale` | 5,000 | throughput benchmark (~1.5 s to generate) |

Eleven anomaly classes are injected at controlled prevalence, with a `--difficulty
{easy,standard,hard}` dial that changes *how much* goes wrong without changing *what* goes
wrong. Money conservation is enforced as a property test: the bank credits reconcile to the
declared settlement nets exactly, modulo the deltas each anomaly explicitly declares.

A committed 60-order fixture set lives in `data/fixtures/dev-standard-42/`.

The data model and the definitions the evaluation depends on are documented in the modules
themselves — `models/truth.py` for the link-level ground truth, `eval/metrics.py` for the
metric definitions, and `money.py` for the integer-minor-unit invariant. The `§` references
in those docstrings point at an internal design document that is not published.

## The demo

```bash
uv venv --python 3.11
uv pip install -e ".[demo]"          # adds LangGraph + Streamlit
python -m ledgerloop.cli demo        # or: make demo
```

About eight seconds: it generates the corpora, fits the calibration bundle on `train` and
`calibration` (never on `test`), reconciles the 60-order `dev` batch through the LangGraph
pipeline, and opens the four-screen interface on the result. It skips corpora that already
exist, so it is safe to re-run. **[DEMO.md](DEMO.md)** has the same steps one at a time,
the prerequisites, and the troubleshooting table.

| Screen | What it shows |
|---|---|
| **Run** | generate or pick a dataset, apply the fitted bundle, reconcile |
| **Results** | precision with its Wilson interval, match rate, recall, exception recall, ₹ reconciled against ₹ outstanding, the tier waterfall, per-class recall |
| **Exceptions** | the queue sorted by ₹ impact, each row with a class, a severity, a price, an evidence chain and a suggested action |
| **Audit replay** | step any record through the tiers: which one proposed it, what it scored, what the policy returned, and why |

`AUTO_MATCHED`, `NEEDS_REVIEW`, `EXCEPTION` and `REJECTED` are always four separate
figures. Unresolved exceptions are shown as unresolved, and the `UNMATCHABLE` floor is
labelled as a real ceiling rather than folded into a failure.

The **Run** tab reconciles any other corpus on disk, including the 300-record `test` split.
Each run writes `reports/runs/<run_id>/` — `run.json`, `audit.jsonl` (append-only, the
replay's source), `exceptions.json`, `decisions.json` — and the UI reads those four files
and computes nothing.

Without the extras, everything that produces a number still works:

```bash
uv pip install -e ".[dev]"
make eval                            # regenerates EVALUATION.md — no LangGraph, no Streamlit
```

## Results

Every number below is regenerated by one command (`make eval`) and written into
`EVALUATION.md`. Nothing in that document is hand-typed and nothing in it comes from a
language model — the metrics are produced by deterministic code, scored against
link-level ground truth read back off disk.

**The four-system comparison**, `test` split, seed 42 (B2 on the 60-order `dev` split):

| # | System | Precision | Recall | Match rate | False positives | FP cost |
|---|---|---|---|---|---|---|
| B0 | Exact join on UTR | 0.5909 | 0.6633 | 0.6580 | 135 | ₹34,98,306 |
| B1 | Exact + fuzzy + nearest amount | 0.6540 | 0.8810 | 0.8667 | 137 | ₹35,37,867 |
| B2 | LLM-only, output asserted unverified | 0.7000 | 0.7119 | 0.9706 | 18 | ₹4,32,588 |
| **B3** | **LedgerLoop** | **1.0000** | 0.4422 | 0.4261 | **0** | **₹0** |

The baselines reach further; every one of them is wrong in rupees. The deterministic
ladder asserts less and is never wrong, and the false-positive column is what that trade
costs a finance team.

**Across five seeds** (`test`, standard difficulty, mean ± sample standard deviation):

```
precision  1.0000 ± 0.0000      recall  0.5808 ± 0.1951
match rate 0.5633 ± 0.1956      exception recall  0.8753 ± 0.0689
0 false positives across all five runs
```

**Each tier, priced** — six ladders × five seeds, thirty runs, zero false positives in
all of them:

| Ladder | Recall | Marginal |
|---|---|---|
| T0 | 0.2154 ± 0.1005 | +0.2154 |
| T0–T1 | 0.3310 ± 0.2156 | +0.1156 |
| T0–T2 | 0.4813 ± 0.1615 | **+0.1502** |
| T0–T3 | 0.5808 ± 0.1951 | +0.0995 |
| T0–T4 | 0.5808 ± 0.1951 | +0.0000 |

T4 fires zero times on this corpus. That is reported rather than engineered around.

**Under load** — the same configuration across the difficulty dial:

| | easy | standard | hard |
|---|---|---|---|
| Recall | 0.8122 ± 0.0641 | 0.5808 ± 0.1951 | 0.4446 ± 0.1156 |
| Exception recall | 0.8267 ± 0.1101 | 0.8753 ± 0.0689 | 0.9088 ± 0.0743 |
| Precision | 1.0000 | 1.0000 | 1.0000 |

Recall falls, exception recall rises, precision does not move: the system asserts less and
describes more as more of the corpus breaks.

**Cost.** The deterministic ladder reconciles the whole corpus with **zero** LLM calls.
Thresholds are fitted on a `calibration` split and never on `test`; the evaluation is
seeded, and two runs of `make eval` produce byte-identical output apart from one labelled
block of measured timings.

## Limitations, stated rather than buried

The uncomfortable numbers are printed in `EVALUATION.md` beside the good ones. The ones
worth knowing before you look:

- **Match rate misses its target.** 0.5633 ± 0.1956 at standard difficulty against a
  ≥ 0.85 goal. The system asserts less than it could, on purpose — the precision column is
  what that buys, and the false-positive column is what the baselines pay for the
  difference.
- **Exception recall is 0.8753 ± 0.0689**, short of the ≥ 0.95 target.
- **T4 fires zero times on this corpus.** Every earlier tier matches at settlement
  granularity, so the partial assignments its rules exist to finish never arise. Reported
  as zero rather than engineered around; loosening a rule until it fired would trade
  precision for the appearance of contribution.
- **The calibrator is single-class.** The residual tiers assert nothing wrong across nine
  corpora, so the logistic has no contrast to learn from and the reliability diagram has
  one populated bin. The threshold is still *fitted*, and the report says exactly what
  that fit does and does not demonstrate.
- **No live LLM was ever run.** There is no provider key in the build environment. The
  production path was measured with a scripted provider driving the real prompts, cache,
  budget, gates and ledger; the LLM-only baseline was answered by a documented stand-in
  reasoner that reads the prompt and nothing else. `EVALUATION.md` prints a banner
  separating measured machinery from what is a property of that rule. **No claim is made
  about any model's answer quality.**
- **`UNMATCHABLE` records are a real ceiling**, not a model failure: 67.6 ± 2.3 records
  per `test` corpus cannot be resolved from the three sources at all. They are excluded from
  the match-rate denominator and reported on their own line, because a system that
  counted them inside its recall could inflate the number by describing items nobody
  could resolve.
- **Synthetic data only.** Eleven anomaly classes at controlled prevalence from a seeded
  generator. Nothing here has met a real bank statement.

## MVP scope

Four scope decisions taken before implementation:

| Decision | Rationale |
|---|---|
| **Neo4j cut** — NetworkX is the real implementation, behind `graph/interface.py` | The plan required both to produce identical decisions, which makes the database pure overhead |
| **ChromaDB cut** — T3 is lexical-only, behind `vector/interface.py` | Sentence embeddings are weak on vowel-dropped abbreviations; a normaliser plus fuzzy matching is better and simpler |
| **Streamlit UI** — React is stretch only | The UI is scheduled after every metric exists; two days is not a React app |
| **A11 FX/multicurrency cut** | Multicurrency forces an FX rounding policy into the money path for 2% of records |
